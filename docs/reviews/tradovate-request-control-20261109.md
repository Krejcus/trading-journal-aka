Základ f5e2f904. Běžící instalace a účty se nemění; migrace je pouze lokální návrh a vyžaduje před aplikací samostatnou zálohu/souhlas. Cílem je odstranit vzájemně nezávislé čtecí smyčky a sjednotit cooldown/budget, nikoli obcházet brokerovu penalizaci.

## 1. Společná identita a autorita

- Broker user ID pochází z již uloženého owner-filtered OAuth řádku `tradovate_user_id`; nový auth/me se nevolá. Key nerozdělovat tokenem, hostem, environment ani AlphaTrade user ID. Neznámá identita nesmí založit další povolený rozpočet.
- Service-only tabulka/RPC v DB autorizuje caller owner+connection a z nich odvodí broker user. Anon/authenticated nemají přímý přístup. Žádný broker network await v DB transakci.
- DB uděluje omezené kredity (grant UUID, count, purpose, validUntil). Celá přidělená kapacita se konzervativně počítá do rolling hour až do validUntil + hodina; nejde o měření skutečně odeslaných requestů. Grant redelivery je idempotentní, jiný payload stejného ID je konflikt. Nepoužitý grant se nevrací.
- Serverová background čtení rezervují jednotlivé skutečné fetch; worker může držet malé předplacené background granty. Výchozí pool4 kreditů, TTL5s, lokální concurrency8/burst16 a DB rolling-minute120 / rolling-hour3000 background budget. Každé okno počítá grant konzervativně do validUntil+window. Hodinový aplikační total soft threshold4000 a rozdíl je zamýšlená kapacita správy; limity nejsou tvrzení o garantované upstream kvótě.
- **Bezpečnostní hranice prvního balíku:** nový soft budget se tvrdě vynucuje na background čtení a před admission nového rizika. Již přijatý lifecycle/fanout, řízení ochran a nouzové writes se nesmějí lokálním vyčerpáním nového soft budgetu zastavit napůl. Nezavádíme jejich novou čekací frontu ani zpětný požadavek na další kredit; skutečná upstream penalizace/captcha stále blokuje všechny kategorie. To je výslovná konzervativní alternativa kritika k celé per-operation write reservation. Neoznačovat ji za tvrdou celkovou globální kvótu všech management writes.
- Background grant redelivery je idempotentní pouze na serveru; worker po restartu zahodí všechny zbytky a žádá nové UUID, nikdy neobnoví celý původní count. DB vrací serverNow a validUntil; deadline grantu se počítá konzervativně z monotonic startu requestu/RTT. Vzdálený zbývající cooldown se naopak ukotví až při přijetí odpovědi, aby RTT nezkrátil brokerovo minimum. Clock jump nesmí otevřít grant ani běžící cooldown. Control-sync výchozí2s, maximální age5s; výpadek blokuje nová rizika/granty, nikoli lokální OFF/Kill. Správa používá lokálně známé brokerové fences a skutečný cooldown; vzdálený stav má přiznanou propagační mezeru.
- Konzervativní aplikační soft budget a management reserve jsou naše řízení kapacity, nikoli upstream garance ani znalost spotřeby cizích aplikací. Entry/background nesmějí čerpat rezervu správy; actual429/captcha blokuje všechny kategorie.

## 2. Worker a persistence

- Jeden registry podle broker user ID v procesu, před startup directory reads. Stejná brána pro raw fetch adapteru, display snapshot/cash/currency, discovery/account reads a všechny WS API requesty včetně authorize/sync. Prázdné protokolové heartbeat `[]` a příchozí stream nejsou nové API requesty; při skutečné penalizaci nesmí vzniknout reconnect/probe storm.
- Node store je mimo group snapshot v pevném service rootu. Atomic0600+fsync/rename; cooldown je monotónní, poškozená či nepřečitelná existující data fail-closed. Chybějící soubor může znamenat první instalaci a vždy vyžaduje úspěšný shared-control sync; samotná jeho absence nezaručuje znalost historické lokální penalizace. Token refresh, reset feedu ani běžný restart uložený cooldown nevymaže. Stav neobsahuje tokeny.
- Finální sync assert a spotřeba kreditu bez await přímo před fyzickým fetch/socket.send, po token/host/read await. Zachovat původní business safety/freshness fences. Wire meter eviduje sent/blocked/response/transportUnknown odděleně.
- Raw429, explicitní Retry-After, endpoint p-time a actual p-captcha neslévat: původ, broker minimum a lokální fallback zvlášť. Raw429 konzervativně1h, actualcaptcha manual/terminal; úspěšná odpověď nerozpustí dřívější cooldown. Display nesmí po raw429 retry za60s.
- Worker přebírá a publikuje sdílený cooldown nejpozději při pravidelném control sync. **Asynchronní propagace není okamžitý globální stop**: po lokálním pozorování již žádný nový dispatch, jiné procesy mají výslovně omezené propagační okno/grant expiry. Při stale/failed control sync nevznikají nové granty. Tato verze nezavádí nový execution fencing dvou Maců.
- Raw429 se lokálně zachytí již z headers před čekáním na body. Pozdější p-time/Retry-After může zákaz pouze zpřísnit. Pokud server nedokáže penalizaci uložit, jeho warm-process registry podle broker user ID zůstane blokovaný; další wrapper nejprve zkusí pouze zápis do DB, nikoli broker probe. Ztrátu celého ephemeral procesu před DB commitem tím nelze odstranit ani vydávat za okamžitý globální stop.
- HTTP423 drží okamžitý lokální inspection hold, nejvýše3s čeká na body a teprve potom ukládá skutečný p-time nebo konzervativní fallback. Krátkých15s v odpovědi se nezmění automaticky na hodinu. Ztráta procesu během tohoto krátkého inspection okna je součástí stejného přiznaného persistence limitu. Post-write potvrzení, které narazí na hold/cooldown, nesmí svůj původní odeslaný write označit `neverSent`.
- Doplňující implementační rozhodnutí pro finálního kritika: obnova známého OAuth tokenu je interní maintenance/management výjimka z nového soft budgetu. Je nutná i pro dokončení přijaté správy. Vyžaduje trusted identity a čerstvý shared-control read s finální synchronní kontrolou, skutečnou captcha/cooldown neobchází. Fetch vracený běžným serverovým čtením zůstává background a device API management grant neposkytuje.

## 3. Úspora čtení a UI

- Display feed má jednu sériovou frontu na připojení, minimální odstup30s mezi account batchi a cache pouze currency metadata. Nemění risk maxAge, eligibility ani skutečné časy dat. Cash invalidace nevytváří nový bulk read každou sekundu. Pro4/8 účtů úplný display sweep může trvat120/240s; to není změna30s rizikového pollu. Průběžné zobrazované PnL bere ověřenou pozici a přesný cenový stream samostatně.
- V governed adaptéru je cash jeden společný `/cashBalance/list` na připojení/poll se singleflight. USD se ověří pomocí `currency/list`, úspěšná metadata jsou vázaná na REST host. Musí existovat právě jeden jednoznačný own USD řádek; chybějící měna, konfliktní nebo duplicitní řádky vracejí chybu, nikdy hodnotu jiného účtu. `/accountRiskStatus/deps` a `/userAccountAutoLiq/deps` zůstávají dvě přesně scopeovaná čtení pro každý účet: jejich `/list` payload dokumentuje jen entity `id`, nikoli `accountId`, a z primárního kontraktu nelze odvodit `id == Account.id`. Přesné přiřazení zaručuje `masterid`, nikoli odhad vazby ID. Nejde tedy o tři globální risk listy. Čas dat je konzervativní skutečný čas čtení, ne omlazený heartbeat. Primární endpointy: [cashBalance/list](https://partner.tradovate.com/api/rest-api-endpoints/accounting/cash-balance-list), [accountRiskStatus/deps](https://partner.tradovate.com/api/rest-api-endpoints/risks/account-risk-status-dependents), [userAccountAutoLiq/deps](https://partner.tradovate.com/api/rest-api-endpoints/risks/user-account-auto-liq-dependents).
- Pouze background `prepare` může čekat na lokální concurrency/burst kapacitu, nejvýše5s, s krátce rezervovaným slotem a novou kontrolou po každém await. Prepared slot se započítá i do budoucího skutečného wire burstu. Přijatý entry/management tento scheduler nepoužívá; finální synchronní dispatch gate a skutečný cooldown stále platí pro všechny.
- Worker-first vypne frontendový Tradovate fulltick/anchor jen u explicitně pokrytých účtů a přesné route/session. Důkaz: úplná baseline + nepřerušený synchronizovaný stream/živý socket, žádný merge/gap/backlog; nejde jen o omlazený heartbeat. Chybějící účet/pozice není flat.
- Serverová čtení používají stejné DB admission/cooldown napříč Vercel instancemi, včetně native widgets/history. OAuth před zjištěním identity je explicitní bootstrap výjimka s dosavadní auth ochranou; refresh známé identity už nesmí obejít cooldown.
- Zobrazované IBKR PnL = přesný kontrakt + čerstvá cena + prokázaná aktuální pozice/fingerprint. Zůstává display-only; nezmění risk, ARM ani exekuční čerstvost. Broker kotva a její timestamp zůstávají samostatné.
- Telefon bere cenu a skutečné nullable bid/ask z nezávislého podepsaného streamu, nikoli z pohybu minutového snapshotu nebo vymyšleného spreadu. Čerstvost přijetí paketu není důkaz času posledního obchodu na burze; zdrojový quoteAt/lastAt dosud nejsou zvlášť podepsaná timing pole. Worker nadále samostatně ověřuje skutečné stáří ceny pro příkazy.
- Execution health je oddělené od transport connected: lokální budget vs upstream cooldown vs captcha vs unknown/stale. Žádné lokálně odmítnuté write označené jako provedené či neznámě poslané. OFF/Kill zůstává lokálně dosažitelné; broker nelze obejít.

## 5. Připravený release postup — dosud neproveden

1. Samostatně exportovat vzdálené schéma a dotčenou konfiguraci/metadata; zálohovat aktuální worker instalaci včetně service-level request-control stavu. Secrets neukládat do Git. Znovu ověřit OFF, flat, no-working, prázdnou relay frontu a přesný cílový source commit; žádné nové funded obchody pro test této změny nejsou schválené.
2. Po výslovném souhlasu aplikovat pouze verzovanou migraci `20261109100740_tradovate_request_control_v1.sql`, ověřit granty/service-only oprávnění a spustit hosted security/performance advisory. Teprve potom nasadit server/web s request-control endpointem a šifrovanou broker identitou v lease.
3. Až po ověření serveru nainstalovat worker ze stejného čistého release commitu. Nová instalace potřebuje trusted broker user ID a nový endpoint; stará samostatná/nepárovaná lease nemá permissive fallback. Zkontrolovat SHA, start, default DISARMED, nezávislé health a read-only reconciliation. Nové UI vyžaduje i aktualizaci fyzického iPhonu pro tuto nativní verzi.
4. Ověřit reálné počty čtení a čerstvost při běžném provozu, vyhrazené DEMO conformance a teprve následně srovnatelné end-to-end latence. Nemíchat to s modelovým replay ani s prokázanou funded conformance. Nikdy nevracet limiter do green resetem nebo testovacími requesty během penalizace.

## 6. Nezávislá oponentura a přiznané hranice

Copier-design-critic prošel26bodový checklist a finální zdroj po opravách. Poslední nezávislé ověření14cílených sad129/129 a čistý diffcheck; verdikt **OK S VÝHRADAMI pro lokální commit po celkových kontrolách**, bez otevřenéhoP0/P1. Opravené nálezy zahrnují header/body závody429/423, nepravdivé notSent po odeslaném modify/cancel, ztracené callbacks v exposure wrapperu, chybějící baseline/owner mapy, expired-state persistence smyčku, skutečný API risk DTO a prepared-vs-wire burst závod. Celkové kontroly a skutečné nasazení jsou samostatný důkaz.

- Workerovy counters zachycují jeho physical dispatch attempts/result, ne broker acceptance. Serverové `brokerCalls` se někde inkrementují již před řízenou admission; nejde o přesný globální wire meter. DB granty měří konzervativní rezervace, nikoli skutečné brokerové požadavky.
- Registry principála drží remote prvního OAuth aliasu; po jeho odvolání může synchronizace zůstat nedostupná i s druhým zdravým aliasem. Zůstává fail-closed, ale jde o mezeru dostupnosti.
- Garance zahrnuje nový pilot composition root a řízené server endpointy. Operátorské `inspectOrders`/`record-*` skripty a budoucí nepoužitý VPS/service root stále mohou vytvořit adapter bez governor. Během penalizace je nepoužívat k probe; jejich samostatné zapojení ani fencing více Maců tato změna neřeší.
- Asynchronní propagace, nezveřejněná penalizace při ztrátě celého procesu a úmyslné smazání lokálního stavu nejsou atomicky vyřešené. Uložený restart cooldown se obnovuje konzervativně a může se tím prodloužit; jednou prokazatelně doběhlá monotónní pauza se uloží jako dokončená.
- Osm účtů se dvěma route má v omezeném replay malou rozpočtovou rezervu. Skutečný celkový provoz, externí aplikace stejného brokera a brokerova vlastní kvóta se musí sledovat po schváleném release; nevydávat model za univerzální dostupnost.
- Fyzický iPhone, aktuální produkční web/worker a broker conformance nejsou tímto lokálním výsledkem ověřené. Zelený transport nebo lokální test nikdy neautorizuje ARM ani funded test.
